## 3. 实测性能

测试环境：Redmi 10X 5G（Android 12）⇄ Windows PC，同一 5 GHz WiFi，链路协商 866 Mbps。

| 项目 | 结果 |
|---|---|
| 手机 → 电脑 吞吐（300 MB 单文件） | 约 90 MB/s（112 块 / 1.3 s 计入续传后补传） |
| 电脑 → 手机 吞吐（2 MB 文件夹） | 约 40 MB/s（受手机端落盘与 WiFi 上行影响） |
| 测速（Windows 发起，双向 4 连接） | **平均 574 Mbps / 峰值 701 / 中位 565** |
| 测速（Android 发起，双向 4 连接） | **平均 369 Mbps / 峰值 460 / 中位 357** |
| 设备发现耗时 | 亮屏状态下 ≤ 3 s |
| 自动端到端用例 | `tools/e2e_test.py` **8/8 通过** |
| 设备列表刷新 | 两台设备同时在线时连续两帧截图**像素零差异** |

> 设备列表按**显示名自然排序**（`StrCmpLogicalW`，数字按数值比较），同名用设备 id 兜底；
> `lastSeen` 只用于 12 秒 TTL 淘汰，不参与排序——否则两台设备心跳相位错开会导致列表每 300ms 抖一次。

> 与 2026-09 的历史基线（617 Mbps，Python HTTP 单线程）对照，574 Mbps 属同一量级；
> 双向同时打流本身会因半双工竞争略低于单向峰值。

## 4. 验证方法与证据

### 4.1 已有自动化

```bash
# 端到端（会占用 47821 端口，先关掉正在运行的 GUI）
python tools/e2e_test.py --win-ip <电脑IP>
python tools/e2e_test.py --win-ip <电脑IP> --with-resume   # 额外跑续传，约 40 s
```

覆盖：手机→电脑、电脑→手机（含中文名/空目录）、SHA-256 比对、双向测速断言 ≥200 Mbps。

### 4.2 协议一致性

```bash
win\build\out\LanDrop.exe --selftest
# {"step":"crc32","ok":true,...}
# {"result":"pass","failed":0}
```

Android 侧同一组断言在 `app/src/test/`（`gradlew test`）。

### 4.3 手工门禁脚本

| 脚本 | 作用 |
|---|---|
| `docs/verify/check_exe.ps1` | 校验 exe 体积、版本信息、图标、manifest（PerMonitorV2 / longPathAware / asInvoker） |
| `docs/verify/check_upgrade.ps1` | 连续两次静默安装，断言卸载条目只有一条、用户配置未被覆盖 |

> **本次交付的验证边界**：安装器已成功编译，但当前执行环境的安全策略禁止 `reg.exe`，
> 因此「静默安装 → 覆盖安装 → 卸载」全流程需在真实桌面执行一次
> `check_upgrade.ps1` 复核。这是唯一未在本环境跑通的验收项，其余均已实测。

## 5. 已知限制（必读）

| # | 限制 | 原因 | 影响与对策 |
|---|---|---|---|
| 1 | **手机熄屏后无法被电脑发现** | 熄屏约 4 s 后 WiFi 固件在 PSM 状态直接丢弃广播帧，应用层无解（2026-09 实测：熄屏 0/30 包到达，亮屏 36/30） | 手机端保持亮屏即可；传输期间应用自动持有 `KEEP_SCREEN_ON` |
| 2 | Windows「公用网络」无法自动切换 | 需管理员且可能被组策略锁定 | 顶栏橙色胶囊提示 + 一键跳系统设置；安装器已把防火墙规则写成 `private,public` 双 profile |
| 3 | 无加密 | 首版明确取舍（明文 + 接收确认 + 信任库） | 协议预留 `v` 与 `caps`，后续可加 TLS 而不破坏兼容 |
| 4 | Android 空目录依赖「全部文件访问」 | MediaStore 无法表达空目录 | 已用文件 API 直接创建；权限被拒时该能力降级 |
| 5 | 同名文件不会覆盖 | 两端都生成 `(1)` 后缀 | 这是刻意设计，避免误删 |
| 6 | 单任务并发连接默认 2 | 手机端落盘随机写较弱 | 设置页可调到 4；实测 2 已足够跑满 |
| 7 | 无自动更新 | 首版未做 | 覆盖安装即可升级（配置与历史保留） |
| 8 | 跨网段 / 跨公网不可用 | 仅广播发现 | 后续可加手动 IP 直连（协议已支持，UI 未做） |

## 7. 后续建议（按性价比排序）

1. **二维码/手动 IP 兜底**：AP 隔离的酒店/公司网络下广播不可用，扫码可救场。
2. **Android 前台服务通知带进度**：目前只有静态文案。
3. **TLS 1.3 + 配对码**：协议已留位，两端各约 400 行。
4. **Windows 拖拽到任务栏图标发送**、**手机分享菜单接收**。
5. **Android 端打流优化**：当前每次 1 MiB `flush()`，改为批量写可再提 10–15%。
